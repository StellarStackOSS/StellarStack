Every permission in StellarStack is a **scope** — a dotted string like
`console.read` or `backups.create`. Subusers carry a list of scopes;
the panel UI hides actions they can't perform; the API rejects requests
that lack the matching scope.

Admins bypass scope checks. Owners implicitly hold all scopes on their
own servers.

## Scope catalogue

### Console

| Scope            | Permits                                              |
| ---------------- | ---------------------------------------------------- |
| `console.read`   | Stream stdout/stderr, see backlog.                   |
| `console.write`  | Send commands to stdin.                              |

### Power control

| Scope             | Permits                                             |
| ----------------- | --------------------------------------------------- |
| `control.start`   | Start the server.                                   |
| `control.stop`    | Graceful stop.                                      |
| `control.restart` | Restart (= stop + start as one locked sequence).    |
| `control.kill`    | SIGKILL.                                            |

### Files

| Scope          | Permits                                                |
| -------------- | ------------------------------------------------------ |
| `files.read`   | Browse, download, decompress.                          |
| `files.write`  | Upload, edit, rename, delete, decompress.              |
| `files.sftp`   | Generate an SFTP password. (Implies `files.read`.)     |

### Backups

| Scope             | Permits                                            |
| ----------------- | -------------------------------------------------- |
| `backups.read`    | List + download backups.                            |
| `backups.create`  | Take a backup.                                      |
| `backups.restore` | Restore a backup over the current files.            |
| `backups.delete`  | Delete a backup row.                                |
| `backups.lock`    | Toggle the lock flag.                               |

### Schedules

| Scope                | Permits                                          |
| -------------------- | ------------------------------------------------ |
| `schedules.read`     | View schedules + their flow graphs.              |
| `schedules.write`    | Create / update / delete schedules.              |
| `schedules.execute`  | Force-run a schedule outside its cron.           |

### Allocations

| Scope                | Permits                                          |
| -------------------- | ------------------------------------------------ |
| `allocations.read`   | View attached allocations.                       |
| `allocations.write`  | Add / remove additional allocations.             |

### Subusers

| Scope               | Permits                                           |
| ------------------- | ------------------------------------------------- |
| `subusers.read`     | See the subuser list.                             |
| `subusers.write`    | Invite, edit scopes, remove.                      |

### Crashes

| Scope            | Permits                                              |
| ---------------- | ---------------------------------------------------- |
| `crashes.read`   | View the crash report list.                          |

### Server settings

| Scope             | Permits                                             |
| ----------------- | --------------------------------------------------- |
| `settings.read`   | View blueprint variables, resource limits, network. |
| `settings.write`  | Edit blueprint variables (user-editable ones).      |
| `settings.rename` | Rename the server.                                  |

## How scopes flow

1. Browser hits an API route.
2. API loads the user's session, looks up their relationship to the
   target server (owner / subuser / admin), resolves the scope set.
3. Route's required scope is intersected with the user's scope set.
4. Allowed → proceed. Denied → 403.

For browser↔daemon WebSocket, the API mints a JWT carrying the same
scopes. The daemon honours the token's scopes locally — no second
round-trip.

## Computing the effective scope set

Given:

- The route requires `console.write`.
- User is a subuser of the server with `console.read` only.

Result: `console.write` ∉ user's set → 403. The UI hides the command
input on render, but the API check is the source of truth.

## Why no roles

Subuser roles ("admin of this server", "manager") were tempting to
add but get fuzzy fast. The atomic scope model is more verbose to
write down, but it's predictable: every action has exactly one scope,
and if you grant the scope they can do it.

The UI layers preset bundles ("Console operator", "Files editor") on
top so the verbose-scope reality doesn't bleed into the click-path for
common cases.
