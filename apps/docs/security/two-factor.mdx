StellarStack supports TOTP (Time-based One-Time Password) 2FA — the
6-digit-code flavour you get from Google Authenticator, 1Password, or
similar. Combined with [passkeys](/security/passkeys), it covers most
operational threat models.

## Enabling TOTP

**Account → Security → Enable 2FA**.

1. Scan the QR with your authenticator app, or paste the secret
   manually.
2. Enter a 6-digit code to confirm the device is set up.
3. Save the **10 backup codes** that appear. Each is single-use and
   replaces the TOTP for one sign-in.

You're now 2FA-protected. The next sign-in asks for your password +
TOTP code.

## Backup codes

Codes are 10 random 8-character tokens generated client-side and stored
hashed. Use one when you don't have your authenticator (lost phone,
travelling, etc.).

Each code:

- Works once; consumed on use.
- Is invalidated if you regenerate codes.
- Can't be used to disable 2FA — that requires the password + a TOTP
  *or* an admin-driven reset.

Regenerate via **Account → Security → Regenerate backup codes**. Old
codes are invalidated atomically.

## Lost your authenticator?

If you have backup codes, sign in with one and re-enrol from the
account page.

If you have *no* backup codes:

- Self-hosted: an admin can reset your 2FA via **Admin → Users →
  \[user\] → Reset 2FA**. This nukes your TOTP secret and backup codes;
  you re-enrol.
- Hosted: contact support with proof of ownership.

There's no email-based recovery — that defeats the point of 2FA.

## Enforcing 2FA org-wide

**Admin → Settings → 2FA enforcement** has three modes:

| Mode           | Behaviour                                                 |
| -------------- | --------------------------------------------------------- |
| **Optional**   | Default. Users opt in.                                    |
| **Encouraged** | Banner prompts users to enrol; doesn't block access.      |
| **Required**   | Users without 2FA can't access anything past sign-in.     |

Switching to Required gives existing users 7 days to enrol before they're
locked out. Admin accounts have a hard requirement to enrol *before* the
mode flip — the panel refuses to switch otherwise.

## Threat model

TOTP protects against:

- Password reuse (the leaked password isn't enough).
- Phishing of the password alone.

It does **not** protect against:

- Phishing of password + live TOTP via a fake panel page (real-time
  relay attack). [Passkeys](/security/passkeys) do.
- Malware on your device that reads the TOTP from your authenticator.

For high-value installs, prefer passkeys over TOTP — same UX, much
better resistance to phishing.

## API + 2FA

The browser session is what carries 2FA verification. API tokens
([API tokens](/security/api-tokens)) bypass 2FA — they're meant for
programmatic access. Treat tokens like passwords.
