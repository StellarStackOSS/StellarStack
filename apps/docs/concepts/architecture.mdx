StellarStack is a four-tier app, but only three of those tiers run as
processes. The fourth tier is your browser, and we treat it like a
first-class node — it talks directly to the daemon for anything that
benefits from low latency.

## The processes

```
Browser ──REST──▶ API ──HTTP──▶ Daemon ──Docker──▶ Containers
   │                  │             ▲
   │                  └──Postgres   │
   │                  └──Redis      │
   │                                │
   └────────WS (console + stats + SFTP)
```

## Why the daemon socket is direct

The naive shape is: browser → panel → daemon. Every keystroke in the
console travels through the panel, every stats sample, every byte of an
SFTP upload. The panel becomes a bottleneck and a bandwidth sink.

StellarStack flips it. The API mints a **scoped JWT** when you open a
server page; the browser presents that JWT directly to the daemon's
WebSocket on the node. The panel doesn't see your console output, your
stats, or your file transfers — it just signed a permission slip.

Benefits:

- **Latency**: typing in a Minecraft console is single-RTT, not double.
- **Throughput**: SFTP uploads of a 4 GB world don't hit the panel at all.
- **Multi-region**: nodes can be on the other side of the planet from
  the panel; only the auth handshake crosses the slow link.
- **Cost**: hosted operators don't pay for transit they don't need to
  carry.

Read [Concepts → Lifecycle](/concepts/lifecycle) for what the JWT
authorises and how scopes are computed.

## Why Docker

Every game server runs in its own container, with bind-mounted persistent
storage at `/var/lib/stellar/servers/{uuid}`. Containers give us:

- **Resource limits** that actually work: cgroups, not the JVM's
  best-guess heap.
- **Reproducibility**: a blueprint is a Dockerfile-ish recipe.
- **Isolation**: one server's plugin sandbox can't write into another
  server's world.

The daemon is the only process that talks to Docker. Browsers don't get
a Docker socket; the API doesn't either. Everything Docker-related goes
through `apps/daemon` and is gated by JWT scope checks.

## State machine

A server is in one of four states:

| State      | Meaning                                                      |
| ---------- | ------------------------------------------------------------ |
| `offline`  | Container not running.                                       |
| `starting` | Container started, blueprint readiness probes pending.       |
| `running`  | Container alive, readiness probes satisfied (e.g. "Done!"). |
| `stopping` | Graceful shutdown in flight.                                 |

`installing` and `restoring` are tracked as **separate columns** rather
than mixing them into the lifecycle state — your server can be `offline`
*and* `installing` at the same time, which is what the UI actually
needs.

See [Concepts → Lifecycle](/concepts/lifecycle) for transition triggers
and probe types.

## Data plane

<CardGroup cols={2}>
  <Card title="Postgres" icon="database">
    Single primary, Drizzle ORM, JSONB for blueprint variables. All schema
    in `packages/db/drizzle/`.
  </Card>
  <Card title="Redis" icon="bolt">
    Status cache (per-server `running`/`offline`), session store, pub/sub
    fanout for panel events.
  </Card>
</CardGroup>

Both are required for the panel + API. The daemon doesn't talk to either
— it has its own SQLite for local state and pushes status changes to the
API via signed HTTP callbacks.
