An **allocation** is a `(node, ip, port)` triple. Each game server has
exactly one *primary* allocation and zero or more *additional*
allocations.

Allocations are admin-managed. End users don't pick raw ports; they
pick "allocation #3 from the pool" and the panel translates.

## Why model it this way

Game-server hosting is full of port bookkeeping. Two Minecraft servers
can't both listen on `25565`. A Rust server needs the game port + a
Steam query port + an RCON port. ARK wants a primary, a query, and a
RCON port that aren't always sequential.

The allocation table makes that explicit so:

- The panel doesn't need to know game-specific port logic.
- Players get human-friendly "default", "rcon", "query" labels.
- Conflicts are caught at allocation time, not at container start.

## Pools

An **allocation pool** is a contiguous range of ports on a node, e.g.
`mc-eu-1, 188.114.97.1, ports 25500-25599`. Creating a pool inserts one
row per port. Pools can be added at node-creation time or later.

The panel never auto-creates pools — they're an explicit admin action so
you don't accidentally expose ports your firewall didn't expect.

## Assigning an allocation

When a user creates a server:

1. The panel filters allocations by node + free status.
2. The user picks one (or auto-picks if only one is free).
3. The allocation is marked taken; its `server_id` column is set.
4. Container create passes `--publish <ip>:<port>:<container-port>/<proto>`.

For multi-port games, additional allocations attach the same way after
the server exists.

## Default vs additional

The first allocation a server gets is its **default** — that's the one
the player tells their friends about (`mc.example.com:25565`). Additional
allocations are typically internal: RCON, query, telemetry.

Only the default is reflected in the public connection string. RCON and
similar are admin-only by default — you can flip them player-visible per
server if your blueprint expects it.

## Releasing allocations

Allocations are released:

- **Automatically** when a server is deleted (cascade).
- **Manually** when an operator removes an additional allocation from
  the server's networking tab.
- **Drained** when a node is decommissioned — the panel rejects new
  placements onto its allocations.

Released allocations stay in the pool, marked free, ready for reuse.

## IP families

Pools are IP-version-specific. A node with both IPv4 and IPv6 needs a
pool per address. The panel does **not** auto-bind IPv6 if you only
configured IPv4 — game clients that prefer v6 will fail otherwise, so
this is conservative on purpose.

## When allocations get weird

<AccordionGroup>
  <Accordion title="A server is using a port not in any pool">
    Almost always means someone changed `server.properties` directly to
    reference a port that wasn't allocated. The container still binds
    inside its namespace; the host port mapping doesn't exist, so
    nobody can connect. Fix: align `server.properties` with the actual
    allocation, or allocate the new port and reattach.
  </Accordion>
  <Accordion title="The pool is exhausted">
    Add another pool, or release allocations from deleted-but-stuck
    servers (**Admin → Allocations → Reconcile**).
  </Accordion>
  <Accordion title="Two servers on the same UDP port">
    UDP doesn't reject double-binds the way TCP does. The Linux kernel
    silently round-robins. The panel prevents this in placement, but if
    you provisioned via API skipping validation, you can hit it. Always
    use the panel's allocation flow.
  </Accordion>
</AccordionGroup>
